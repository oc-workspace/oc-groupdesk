# chatlog-keeper / Linux 微信兼容性验证

日期：2026-11-02。目标服务器：`rococo-root2`。本次仅做验证，未部署长期运行的聊天记录服务，未变更 GroupDesk 或 Hermes。

## 固定版本与验证边界

- 上游：[labazhou2024/chatlog-keeper](https://github.com/labazhou2024/chatlog-keeper)，提交 `2225294fd0761e10ce15540f21e7dbb2ac304c3c`，包版本 `0.3.7rc0`。
- 实际微信：官方 Linux x86_64 `4.1.13.23`。
- ELF SHA256：`2ca28ea56b1a400543d0128ebaf0b93f88172dd66dc0426d3d74fdb971eab959`。
- ELF Build ID：`ce28c3471d532eeb1f136482eeb4d0bdfd59c06e`。
- 取钥验证经用户明确授权。仅以微信用户 UID 1000 操作，密钥不得显示、上传、写入文件或缓存。初轮验证不重启微信；用户随后另行明确授权受控重启在线微信，完成启动期取钥与真实解密验证。
- 离线启动验证仅使用独立容器中的私有数据副本，网络为 `none`，不发布端口，不挂载生产数据目录。
- 原始微信容器启动时间：`2026-10-29T18:57:31.559493286Z`。

## 已完成的检查

1. 微信程序的指令特征匹配上游 `locate_kdf_boundary()`，密码派生与 HMAC 派生特征均通过唯一性检查。
2. 实际程序与隔离环境的微信程序 SHA256 一致。
3. 微信自身用户可以加载读取模块，识别到一个微信主进程。
4. 同用户限时只读内存扫描：数据库一致性副本创建成功；25.30 秒内未找到通过数据库 HMAC 校验的密钥。未使用调试器附加到生产进程，未写入密钥。
5. 已对隔离数据副本中的 6 个数据库文件族刷新一致性快照，包含消息、联系人、通用配置和会话库。

静态特征匹配仅说明可以尝试启动期取钥，不能单独证明已成功解密或完整支持该版本。

## 离线启动及实际解密

- 临时 Ubuntu 验证环境完全断网，不增加进程权限，原微信程序及配置不变。
- GDB 的 Python 支持、AES 库加载均通过。
- 上游相关测试：`82 passed, 1 skipped`，覆盖 Linux KDF 定位、同用户读取、取钥候选校验与快照一致性。
- 独立容器使用私有副本启动微信，运行 61.04 秒，结果：`capture_timeout`，`observer_hits=0`，`observer_candidates=0`，未取得密钥，未解密消息库。
- 该结果不能证明版本不兼容：离线副本没有触发数据库取钥边界。上游的在线启动取钥和实际数据库 HMAC / SQLite 检查仍未完成。
- 没有提取到可用密钥，没有密钥文件，没有导出的聊天内容，没有发送群消息。

## 受控在线启动与真实解密

- 用户授权临时中断机器人收发后，保存原收发开关与巡检状态，暂停收发和整点自动恢复；不改动群配置、Persona 或模型。
- 真实容器预检通过：UID 1000、原微信 ELF 指纹、桌面会话、GDB Python、AES 均正常。
- 以原微信用户退出日常进程后，使用上游的启动期硬件断点取钥流程。用户手动完成桌面登录及所需确认。
- 上游观察器命中 1 次、产生 1 个候选；候选通过真实消息库 HMAC 后才被接受。
- 消息库、联系人库、会话库共 **3/3** 个数据库的 HMAC 校验通过。
- 消息库完整解密及 SQLite `PRAGMA quick_check` 通过，返回 `ok`。
- 消息库有 4 张会话表、1021 行消息记录。上游解析器输出 **752 条消息，其中 727 条文字消息**。数据库行数不等于解析器导出消息数，不能据此宣称全部类型均已支持。
- 本轮用时 226.22 秒（包括等待人工登录），验证结束后已启动普通微信；普通微信主进程为 1669865，调试器已退出。
- 密钥不显示、不上传、不写入缓存文件；FIFO 仅用于内存传输。临时明文消息库位于 `/dev/shm`，查询结束即删除。仅保存计数和校验结果。

## 当前结论

**当前服务器的官方 Linux 微信 4.1.13.23 已通过实际取钥、数据库解密和消息解析验证。**

结论限于此 ELF 构建、此上游提交与本轮验证的文本/消息数据库。未验证图片、语音解密、所有消息类型或未来微信升级。Chatlog-keeper 本身是 CLI，持续服务、增量读取和 GroupDesk 接入尚未部署。
