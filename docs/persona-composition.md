# 基础 Persona 与特色 Skill 组合

每群一个基础 Persona，可搭配零到五个特色 Skill。基础负责整体声音、语言习惯和事实边界；特色只增加适合当前语境的表达技巧，例如接梗、教学或写作节奏。不是运行两个角色，也不会为每个 Skill 分别发起模型调用。

「从容迎新」另有显式运行时调度协议：群友明确介绍新人后随机等待15—40秒再准备欢迎，仍受群参与、话题与配额约束。普通表达特色仍不增加触发权限。详见本页「从容迎新特色」。

## 使用

1. 在「Persona 制作 → Persona 技能」新增 Skill，选择“基础 Persona”或“特色 Skill”。已有 Persona 按基础类型保留，已发布后不能改类型；要拆分旧专项，另建特色并保留原版本。
2. 人工维护或用素材生成草稿。特色只写适用语境、增量技巧、收敛条件和少量合成示例，不复制基础人设。特色完整 SKILL.md 最多6000字符。
3. 发布不可变版本。草稿保存、版本发布、群绑定仍分开。
4. 在「群人设配置」单选基础，勾选特色，并选择各自的版本与跟随方式。可查看已保存组合；有未应用选择时，预览明确显示它仍是已保存配置。

“跟随最新发布”只跟随正式发布的版本，不跟随草稿。发布会更新相关群的实际版本ID并增加群revision，等待机器人确认；其他群和固定版本不变。固定旧版本可以用于观察或回退；恢复跟随后立即解析到该Skill最新发布版。组合正文最多3万字符，超过限制时整个绑定或发布事务取消，不能有的群更新、有的群静默失败。

同一个特色只选一个版本。顺序按选择顺序保存并纳入组合摘要，但排列不授予覆盖权限：群策略优先，基础其次，特色只做兼容补充。特色互相冲突或不适用时退回基础表达。认真问题先完成实质回答。勾选特色不新增参与触发条件，不提高发言次数或token预算。

## 维护与兼容

- `personas.kind`区分基础与特色；`persona_versions.kind`记录发布时类型，版本正文和来源保持不可变。
- 原`groups.persona_version_id`继续保存基础发布版本；新增`persona_follow_latest`。旧群默认固定原版本，不自动迁移或改变风格。
- `group_persona_features`记录群、特色Persona、实际发布版本、顺序和跟随开关。同一群同一特色唯一，并有版本归属外键。
- 历史客户端只更新基础绑定、没有提交features字段时保留已有特色；新版界面提交完整列表，空列表表示主动取消全部特色。
- 被任意群作为基础或特色使用的Skill不可归档；归档不删除历史。已有完整专项仍可作为旧基础版本回退，不原地改写成特色。
- 跟随更新会使在途旧群配置失效，沿用原有配置revision和发送前复核；不把旧配置答案发到新策略下。

`skills/gt-banter/SKILL.md`是第一份独立特色，从旧完整专项中提取增量技巧，通用GT规则保留在基础Persona。运行时实际使用数据库发布版本；仓库文件是可复现的起点，不会覆盖管理员后来保存的草稿或发布版本。

## 适配器契约

保留`persona_contract_version=1`及`persona_skill`基础字段；新增有序`persona_feature_skills`。有特色的群下发`persona_composition_contract_version=1`及`persona_composition_sha256`。

组合摘要为以下紧凑JSON数组UTF-8的SHA-256，元素只含ASCII版本ID与摘要，不含正文：

```text
[1, base_version_id_or_null, base_sha256_or_null, [[feature_version_id, feature_sha256], ...]]
```

机器人校验基础、每个特色的摘要、归属、数量与总长度，合并成一个可信系统绑定。特色情境规则不是额外工具权限；群语言、身份、话题与额度规则最后继续加入。切群、取消特色或更换版本时替换此前绑定，不在历史里叠加旧特色。请求审计只记组合摘要与ID，不额外记录聊天正文。

有特色时ACK必须提交`persona_composition_version=1`和匹配的`persona_composition_sha256`，同时保留原基础Skill摘要。旧适配器、部分组合或错误摘要不能确认。普通基础-only群仍接受原Persona能力字段。JS客户端要求apply回调实际应用完整组合后返回能力；MaiBot每次同步先校验再ACK，失败即停止该群，不能静默只加载基础。

互动文案缓存也使用组合摘要，避免签到等文案沿用旧人设缓存。特色会增加输入长度和token消耗，但不为组合本身增加模型调用次数。仍共享原有预算。

## 拆分旧专项

`scripts/migrate-persona-composition.ts`是显式运维迁移，不由数据库升级自动执行。管理员选定群ID、预期revision、旧专项发布版本和基础版本，通过stdin提供。脚本从仓库读取GT接梗特色，保留来源版本、摘要和原素材来源；原完整专项和版本不删除。

迁移只改变指定群的基础与特色绑定，默认两者跟随最新发布；原语言、身份、话题、模型和额度不变。并发修改或同名特色内容冲突即取消事务。重复执行同一成功迁移不再增群版本，不覆盖后来编辑。先更新适配器、验证契约，再执行；不要靠向真实群发送测试消息验证。

## 验证与回退

Node单元测试覆盖组合身份、类型、边界和客户端ACK。隔离PostgreSQL集成测试覆盖两群不同组合、两个特色、固定/跟随、草稿不生效、发布原子回滚、归档限制、旧API兼容和显式迁移幂等。MaiBot断网测试使用原生请求类和合成材料，验证完整绑定、旧特色移除、摘要错误拒绝以及正常GT/中性兼容。

发布前按既有脚本备份数据库和files。日常回退优先把群选回旧基础版本并取消特色，保留记录与新表；不要删除历史版本。若退回旧适配器，必须先取消特色，否则ACK会明确拒绝。数据库整体恢复与应用版本回退需配套，按原部署文档执行。


## 公开基础Persona模板

2026-11-05新增两份自包含群聊模板，统一为基础类型，显式导入后发布v1，供管理员按群选择，不自动更换群绑定：

| 名称 | 风格与范围 | 来源处理 |
|---|---|---|
| 巴菲特风格 · 价值投资 | 耐心朴素，关注长期价值、商业质量、现金流与风险；普通话题不强套投资报告 | 参考`agi-now/buffett-skills`固定提交`aeeae92c22c4770cd1277a35d37294c9c2435475`；该提交未见许可证，因此独立撰写通用框架与群聊规则，不搬运原文或8份参考文件 |
| 马斯克风格 · 第一性原理 | 直接简洁，重目标、约束、实验与工程迭代；不强制长回答 | 参考`OpenDemon/elon-musk-skill`固定提交`24e76e8ecf3e31873529f1f00424b65a3369fb60`做群聊适配；保留MIT版权/许可声明 |

原仓库的外部文件Read要求、自动覆盖所有话题的触发规则和固定报告长度不直接移植。两份模板只使用已提供资料，服从本群语言、身份披露、话题、篇幅及频率；不冒称人物本人或虚构其内幕、持仓与背书。模板为公开通用角色，不含用户聊天或据私人素材生成的人设。

运维显式运行`tsx scripts/bot-exec.ts <机器人UUID> seed-public-base-personas`。每个空间独立产生Persona与版本ID；同一公开模板可在各账号各保存一份，不共享素材、群绑定或后续编辑。已有同名基础Persona完整保留，重复导入不更新草稿或正式版本；同名特色冲突时拒绝。没有自动跟随GitHub上游，更新需审查后另建草稿并按既有发布流程处理。

素材无需另行勾选。导入后在「Persona 制作 → Persona 技能」可编辑，随后保存/发布新版本；在「Persona 制作 → 群人设配置 → 基础人设与特色 Skill」为目标群单选一个基础Persona并保存应用。不同群可以分别选择GT、巴菲特、马斯克等基础，特色仍可组合。两个新增项均已发布v1，尚未选用时不会触发机器人更新确认。

来源提交、许可、改编方式及包SHA256保存在草稿/发布版本来源字段；Musk完整MIT声明同时保存在仓库`LICENSE.upstream`和导出包`references/provenance.json`的license_text中。生成后的个人修订不被重导入覆盖。

两份v1现已在RyuBuddy和Tatsumi两个已有空间独立导入。各空间原有GT基础与特色、全部群选择保持原值；导入只增加可选项，不自动修改任何群。当前每空间有4个可选已发布基础；RyuBuddy另外的未发布基础草稿仍保留。


## 群管理的人设入口

基础与特色只在「Persona 制作 → 群人设配置」选择、保存与应用。群管理的「参与、人设与语言范围」移除旧 GT/中性下拉，改为展示已保存基础名称、版本与特色列表；机器人是否已应用仍由本群配置确认状态表示。已绑定发布基础时不再展示或编辑被覆盖的旧备用字段，普通群配置保存继续保留它，不迁移或重置已有绑定。未绑定发布基础的旧群会明确显示当前沿用的内置人设，并引导前往统一入口。

「前往本群人设配置」打开当前机器人空间的 Persona 制作、直接选中群人设配置及目标群。群配置有未保存修改时先提示保存，避免跳转丢草稿。正常从侧栏进入 Persona 制作仍先展示 Persona 技能，群人设配置可筛选单群或全部群。身份说明文案沿用本群选中的 Persona，不再固定描述为GT。

## 从容迎新特色

`newcomer-welcome` 是独立特色 Skill，可与 GT 基础 Persona 和其他特色组合。初始化脚本仅建立待人工确认草稿，不自动发布或修改群绑定；运行端已支持下述计时协议，具体群是否启用以后台已发布绑定为准。

### 后台操作

在「Persona 制作 → Persona 技能」中打开「从容迎新（待人工确认）」，检查、修订、保存并发布。随后到「基础人设与特色 Skill」，保留该群现有基础和特色，另勾选本特色，点击「应用组合到此群」。手动刷新查看机器人确认。

保存草稿不会改变群配置。移除此特色会关闭本群迎新触发，并使旧版本待处理欢迎失效。每个群仍可选择固定发布版或跟随最新发布版。

### 实际计时

只有明确介绍新群友的消息才触发，首版识别中文、英文和日语的保守表达，不依赖桌面客户端提供入群系统事件。普通问好、活动欢迎、欢迎回来、引用、示例和讨论“怎么欢迎新人”不会作为迎新触发。其他语言识别可后续扩充；未识别不强行插话。

程序先在 SQLite 持久队列抽取15—40秒（含端点），到期才允许准备简短欢迎。等待不占用模型请求，重启或重复消息不会重抽。15—40秒是准备前的随机等待，模型生成另需时间；自原介绍起90秒仍未完成则放弃，避免过时补话。

同群等待期间的多条明确介绍合并成一轮，不重置计时；120秒内不再创建新轮。该窗口是轮次合并，不声称已根据微信号识别同一人。其他人已经欢迎时由模型根据近期背景轻接一句或保持安静；正事、明确不适与静默优先。

同一介绍者随后点名机器人或问实质问题时，取消其可选欢迎，让普通请求进入原队列。欢迎走原有被动发言配额、目标群、语言、预算、版本和最终发送校验，不提高额度；仅点名模式、安静模式不会获得主动迎新权限。严格“所有回复仅限已选话题”模式仍要求介绍命中所选话题。

计时策略通过显式 `newcomer_welcome_contract_version:1` 下发，并要求 `newcomer_welcome_policy_version:1` 确认。旧适配器不得仅应用 Persona 正文就确认支持随机计时。时长由程序协议控制，编辑 Skill 正文中的数字不会修改程序计时。

### 部署与验证

GroupDesk：遵循开发服务器 `oc-push`、发布桥 `oc-prod-release`、核对PR提交/差异、合并main、生产备份和Docker发布流程。

原生适配器：`integration/maibot/welcome/install.py` 对经审核基线做摘要检查，只安装队列与可信提示钩子；新增 `newcomer_welcome.py`、更新 `groupdesk_runtime.py`。部署前在固定MaiBot镜像里使用当前源码与隔离SQLite测试，暂停桥接新入队，等待现有任务结束，再备份和仅重建MaiBot及bridge。保留微信容器和已有配置、账本、密钥。

显式运行 `npx tsx scripts/seed-welcome-persona.ts` 仅创建一次草稿；同名记录存在时保留人工修改，不覆盖、不发布、不绑定。不向真实群发送测试消息。
