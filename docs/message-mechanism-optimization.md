# 微信机器人消息机制优化方案

更新日期：2026年11月7日，Asia/Singapore。实施状态：设计已记录，运行机制待开发与验收。

本方案面向 `oc-workspace/oc-groupdesk` 管理的 Linux 微信机器人，优化收消息、判断回应、生成、跨群排队、发送和人工接管的完整过程。目标是让机器人能等人说完、适时开口、避免抢话，并在多个群之间遵守同一微信账号的发送节奏。

同一微信账号的所有自动发送必须经过统一出口。读取继续使用 Chatlog Reader，发送继续接入现有 Bowxt 界面队列和独立回执核对；本方案不以原生注入发送为前提。以后更换传输组件时，也必须保留相同的队列和校验契约。

全局最小发送间隔尚未选定。下文的 30 秒仅用于演示，合并及接管参数属于拟议初值，都没有因保存本文而改变线上设置。这些数值服务于交互体验和资源调度，不是微信官方安全阈值，也不构成不触发账号风控的保证。

## 现有基础与优化范围

当前项目已有数据库来源、稳定消息身份、来源去重、按群权限、成员跟进、共享模型预算、请求截止时间和发送后回读。新机制应接入已有账本，避免建立第二套互不相认的任务、配额或发送记录。

| 环节 | 已有基础 | 本方案的增量要求 |
| --- | --- | --- |
| 消息读取 | Chatlog Reader 通过 Linux 文件事件增量归档，提供群和账号边界 | 保持事件驱动，不为回复节奏增加空闲原库扫描 |
| 消息合并 | 运行适配器已有合并与有限等待逻辑 | 明确同账号同群同成员的合并范围、最长等待和更正处理 |
| 回应资格 | 点名、话题、跟进、轮数和预算共同门控 | 减少无必要插话，分离是否回应与何时发送 |
| 发送 | Bowxt 队列、幂等请求和数据库独立回执 | 增加账号级统一调度，覆盖跨群和各类自动发送 |
| 过期与恢复 | 点名请求、主动插话、总结和恢复任务各有契约 | 等待不延长原截止时间；发送前复核最新上下文 |
| 多机器人 | 不同微信账号的资料、队列、密钥和账本独立 | 同账号跨进程协调，不把不同账号的内容或记忆合并 |

详细现状见[群内回复控制](reply-controls.md)、[按群配置等待时间](group-timeouts.md)、[多机器人管理](multi-bot-management.md)和[读取器运行说明](../integration/chatlog-reader/README.md)。

## 一次回复的处理流程

```text
来源消息入库和去重
  → 按成员收集合并
  → 判断回应资格与当前话题
  → 形成带绝对截止时间的任务
  → 生成候选回复
  → 进入账号统一发送队列
  → 等待节奏与账号发送许可
  → 复核上下文 权限 配置和人工接管
  → 触发唯一传输组件
  → 核对发送结果并更新跟进资格
```

等待合并、等待模型和等待发送需要分别记录。界面可显示真实的“等待补充”“正在生成”“等待发送”“核对送达”，只有得到有效送达证据才显示“已发送”。不以虚构的打字状态、在线状态或个人经历解释程序等待。

所有阶段共享原任务的绝对截止时间。补充、催促、重试、跨群排队和进程重启均不重新起算；生成完成也不代表可以忽略发送时效。队列工作通过事件和到期时间唤醒，等待期间释放数据库事务和模型并发名额。

## 收集连续消息与处理更正

合并键使用经过来源核验的账号、群和成员稳定标识。相同昵称、相同正文或两个分库里相同的数字行号都不能替代稳定身份，不跨群合并成员的发言。

建议先以最近一条消息后 3 秒安静窗口、首条消息后最多 12 秒作为离线验证初值。任一条件达到即停止等待；最长等待和任务截止时间更早到期时，以更早者为准。参数需要与当前快速回应、点名、自然参与和迎新策略逐项兼容，不能用一个固定等待覆盖所有入口。

同一成员的连续补充可以合成一轮输入，但保留每条来源 ID、原始发送时间与首次采集时间。已经生成时收到实质更正，应使旧候选失效，再按剩余时限处理最新版本；限制重生成次数并计入原任务预算，避免不断补充导致无限生成。

“算了”“不用回复”只有在能可靠对应本群该成员的待处理请求时才取消。无法确认指代时保持上下文判断，不用一个群友的普通发言取消其他人的任务。重复来源和重复催促不新增模型任务。

## 判断是否回应

明确点名、可信引用机器人，以及成功回复后仍有效的同成员跟进，优先于可选的自然参与。群权限、话题模式、轮数、语言、配额和请求时效始终共同生效，优先级不能授予新权限。

自然参与先经过已有规则过滤，再使用任务本来需要的上下文判断：问题是否已经解决、是否在对机器人说话、当前是否适合加入、是否存在明确不适或拒绝。跳过无需回应的内容，不为每条群消息单独增加一次模型判断请求。

多个成员的对话状态分别保存。其他人插话不会自动剥夺原成员的跟进资格，也不能继承别人的资格。跟进窗口仍从已确认成功发送完成计时，排队、生成完成、发送预留和未核实回执均不计为成功回复。

## 回复时机与表达

回应资格确定后，再决定最早适合发送的时刻。简单确认、正在进行的问答、长消息和复杂任务可以使用不同等待策略；已经花在合并、生成和排队上的时间应计入等待，不在模型完成后机械追加一整段延迟。

候选任务可携带 `reply_not_before`。调度时同时满足业务等待、账号全局间隔和原截止时间，等待本身不消耗新的模型调用。额外阅读等待应可关闭，并设置上限；具体参数先通过离线场景确定，不用随机抖动掩盖异常使用。

一轮优先形成一条完整、简短的回复，随问题复杂度调整长度。必须拆成多条时，每条真实消息都重新经过全局发送门控，不能把一组消息算成一次发送后连发。长报告继续遵守已有总结流程，不为了聊天口吻破坏报告结构或完整性。

Persona 决定语气，不虚构“刚忙完”“刚看到手机”等现实经历，也不为了显得像人而故意写错。耗时提示和致歉沿用现有规则，尽量与最终答复合成一条，不新增例行的“收到”“稍等”“正在输入”刷屏消息。

## 同一微信账号的全局发送间隔

### 作用范围

全局限速键必须绑定到经过核验的微信账号。机器人 UUID、群 ID、适配器实例 ID 或容器名只能辅助定位，不能让同一个微信账号因为换群、换进程或重启而得到新的额度。账号指纹仅作私有运行标识，不输出原始账号目录或密钥。

以下自动发送统一经过门控：普通回复、跟进、自然参与、迎新、签到与兑换回复、总结发群、恢复补答、管理员通过系统提交的微信消息，以及明确允许的发送重试。只查询回执不算发送；使用独立外部通知通道的告警按其自己的账号和契约处理。

不同微信账号维持独立队列与资料边界；共享宿主机资源预算继续生效。本方案不改变当前机器人启停或先后切换规则，也不自动启用多账号并发。

### 间隔的计算与实际发送边界

设最小间隔为 `G`。上一条发送安全释放时记录 `last_guard_at`，下一条最早可发送时刻为：

```text
eligible_at = max(last_guard_at + G, reply_not_before, existing_business_due)
```

若 `eligible_at` 已达到任务绝对截止时间，则任务过期，不触发发送。其他群的高优先级请求也不能绕过 `G`。

节流必须约束实际触发微信发送的出口。只在模型开始前等待、HTTP 入队前休眠，或只限制调用 `send_text` 的次数，都不能保证底层队列真正按间隔发出。现有 Bowxt 需在最终执行层验证发送许可；以后原生传输组件也需遵守相同约束。

每账号同时只允许一个真实发送操作处于执行中。`last_guard_at` 取可确认的传输执行完成或安全释放时刻，晚于已知实际提交时刻时采用更晚值，保守计算下一次间隔。传输仍在执行或无法确认旧执行者是否停止时，不释放该账号发送许可。

传输已明确结束但业务送达仍待核实时，可以在上述间隔后处理下一条独立消息；原任务继续保持待核实，不能凭等待结束认定成功，也不能自动重发。明确发生在提交前的失败可以按有限重试规则再次排队，重试仍受门控。

例如仅用于演示的 `G = 30 秒`：若群 A 的上一条发送在 12:00:00 安全释放，群 B 最早在 12:00:30 开始；若群 B 在 12:00:32 释放，群 C 最早在 12:01:02 开始。不能让三个群各自拿到一条立即发送的额度。

### 跨进程协调和重启

一个账号使用唯一的发送协调者和持久账本；多个桥接、任务执行器或容器必须调用同一个协调者。进程内锁或每容器独立 SQLite 都不能单独实现跨进程全局保证。通过事务原子领取任务，并使用递增执行代次阻止旧执行者继续派发；最终传输出口也必须校验代次。

发送请求至少持久记录账号作用域、目标群、幂等请求 ID、来源任务、截止时间、配置修订、执行状态、底层队列 ID 和节流时间。沿用现有发送账本作为事实来源，迁移时明确字段映射，不建立互相覆盖的成功记录。

崩溃恢复先查原请求和底层队列。已提交、结果未知或执行中的请求进入核对；未提交且仍有效的请求才重新排队。租约到期本身不能证明旧进程已停止发送，不能仅凭到期抢占。恢复不清空全局间隔、不重置截止时间、不补发全部历史。

进程内等待使用单调时钟；跨重启时间持久保存。检测到明显时钟回拨、账号绑定变化或发送状态不一致时暂停派发并报告原因，核对后再恢复，不把异常解释为间隔已过。

### 手动发送的边界

账号主人直接在微信里发送，发生在机器人出口之外，程序无法强制拦截。因此可强制保证的是本系统管理的自动发送间隔，不能承诺所有手动消息与自动消息之间也必然达到 `G`。

数据库读到未经本系统发送账本认领的本人消息后，触发相应群的人工接管，并保守更新本账号发送保护时间。若需要更严格的人机互斥，应先在后台暂停自动发送、等待在途操作结束，再开始人工操作；数据库观察延迟不能作为同步锁。

## 跨群排队与发送前复核

队列优先处理有效的点名及正在进行的问答，其次是有明确业务时效的任务，再处理可选自然参与。优先级只改变排队顺序，不绕过全局间隔、账号暂停或群权限。

同优先级按群轮转，群内按业务顺序处理；同群连续发言要让出机会给其他已就绪群。为低优先级任务设有限等待或随等待提高优先级，始终受原截止约束。队列满时优先拒绝或取消尚未提交的可选插话，不让旧任务因排队获得新时效。

发送前必须重新检查：

1. 微信账号、目标群和来源身份仍与绑定一致，机器人和群仍启用。
2. 当前配置租约、权限、Persona 与任务修订仍有效；配置撤销后旧候选失效。
3. 未处于人工接管，来源任务未取消，消息未过期，账号最小间隔已满足。
4. 新上下文是否包含明确更正、取消、已解决或继续等待的指示。
5. 来源任务、内容版本和幂等 ID 是否已提交、已发送或待核实，避免重复发送。
6. 当前模型、群、成员和发送预算仍允许本次操作。

稳定的结构化取消与权限变化直接处理；需要语义重评估时有界调用，并计入原任务预算。普通新消息不应自动触发整段回复重生成。已进入不可撤销传输阶段的操作不能显示为已成功取消，应继续核对实际结果。

## 人工接管

接管来源包括管理员主动暂停，以及读取到未被系统账本认领的本人手动发言。系统自己的回复和迟到回显不触发人工接管；无法判定来源的本人消息按待核实处理，避免形成机器人回复自己的循环。

默认只接管对应群，保留其他群的独立对话；账号级手动暂停则停止所有群的自动派发。建议自动接管初值为 120 秒，最终时长可配置；管理员主动暂停必须由管理员明确恢复，不能靠定时器自动解除。

接管期间继续按原权限登记来源，不新增自动回复，也不将手动发言当成机器人成功回复。尚未提交的候选取消或标记需重新判断；在途发送继续核对。定时接管结束后从当前边界恢复，新请求正常处理，不自动补发接管期间积压的旧答案。

## 配置与管理界面

以下是拟议字段和初值，不是当前已发布的 API、数据库列或运行参数。实现时应优先复用现有配置结构，并通过版本契约区分新旧运行端。

| 拟议配置 | 作用域 | 初值或待定项 | 生效规则 |
| --- | --- | --- | --- |
| `account_send_min_interval_seconds` | 微信账号 | 待管理员选定，30 秒仅为示例 | 启用时必须为正数；所有群和自动入口共用 |
| `merge_quiet_seconds` | 群和消息类型 | 建议 3 秒 | 首条起最长等待与任务截止优先 |
| `merge_max_seconds` | 群和消息类型 | 建议 12 秒 | 新补充不延长最长等待起点 |
| `reply_not_before` | 单个任务 | 按上下文计算 | 合并、生成和排队已花时间计入等待 |
| `manual_takeover_seconds` | 群 | 建议 120 秒 | 不覆盖管理员主动暂停 |
| 自然参与冷却 | 群 | 复用现有参与策略 | 不修改点名权限或共享预算 |
| 队列上限与各类任务时效 | 账号和任务类型 | 复用现有约束 | 不以新的统一 TTL 覆盖总结、点名或恢复任务 |

全局间隔放在当前机器人或账号的发送设置中，不能放在每群独立配置中伪装成全局控制。界面显示当前有效值、待应用版本、队列状态、最早可发送时间和阻塞原因；保存后须由实际出口应用并确认能力，旧运行端不能误报已生效。

提高间隔时，所有尚未触发的发送立即遵守新下限；降低间隔不得撤销已持久预留的保护时间。已有任务的绝对截止不变。新字段缺失时保持旧配置兼容，不能静默启用一个管理员尚未选定的间隔。

点名任务继续遵守现有按群总有效期，默认 420 秒；普通主动插话继续保留 90 秒时效。总结、恢复补答及接入问候沿用各自任务契约；迎新特色已有的 15 至 40 秒准备等待也不能绕过账号出口。现有模型重试、预算和致歉规则见[等待时间说明](group-timeouts.md)，迎新细节见[新人欢迎](newcomer-welcome.md)。

## 可观测性与验收

运行状态应能区分等待补充、等待模型、等待账号间隔、人工接管、配置失效、任务过期、发送执行中和送达待核实。按账号统计排队时长、取消和过期原因、实际派发间隔、有限重试次数和不确定发送数量，不在常规指标中保存聊天正文、密钥或完整账号标识。

用可控制时钟、合成来源消息、隔离账本和假的传输组件验证机制。不得为自动测试向真实微信群发送消息，也不把模拟结果写成真实送达证据。

| 验收场景 | 必须得到的结果 |
| --- | --- |
| 同成员连续补充或催促 | 有界合并，保留首条时刻，不重复创建任务或续期 |
| 两名成员同文及跨群同名 | 来源分别登记，不串人、不串群、不共享跟进资格 |
| 三个群同时有候选 | 同账号实际派发满足 `G`，按群轮转，无并发绕过 |
| 两个进程争抢同一账号 | 原子领取，只发生一次真实提交；旧代次无法继续派发 |
| 不同账号独立排队 | 队列和记忆隔离，不因同宿主机合并账号节奏 |
| 总结与普通回复或迎新同时到期 | 都走相同账号出口，原配额和各类截止仍有效 |
| 生成后出现取消或更正 | 未提交旧候选失效；重生成有界且共用原预算和截止 |
| 人工发言及机器人自身回显 | 手动消息触发接管，自身已知回显不误触发 |
| 接管结束或重启恢复 | 建立当前边界，不重放过期答案；节流状态保留 |
| 发送调用超时或进程崩溃 | 查询原幂等请求，未知结果不盲目重发或切换传输 |
| UI 已入队但尚未真正执行 | 不将入队当成已发送，不提前释放账号执行许可 |
| 发送失败与迟到服务器回执 | 原任务状态正确收敛，不重复发送，不重复计轮数 |
| 排队超时及暂停或配置变更 | 过期或失效任务不提交，暂停不被自动恢复绕过 |
| 时钟回拨及运行端缺少新能力 | 保守暂停或拒绝确认，不假称下限已生效 |
| 空闲群没有消息 | 无新增模型调用、原库周期扫描或群内状态消息 |

实际间隔验收以假的传输组件执行时刻为单元测试依据，以真实出口的可核对记录为运行验收依据；模型开始时间、HTTP 入队时间和归档观察时间不能冒充真实派发时刻。

## 实施顺序与回退

第一阶段在当前适配器和发送账本中完成账号统一调度、跨入口接入、持久间隔和重启恢复，先封住所有自动出口的绕行路径。每个同账号调用方都接入后，才能声明全局保证。

第二阶段补齐合并、更正、发送前复核、人工接管和跨群公平性。优先复用现有门控与生成链路，保留当前群、Persona、预算、历史来源和配额；只在需要变更的接口引入新版本。

第三阶段提供管理设置、真实运行能力确认和清楚的等待状态。先兼容部署运行端，再下发并启用已选定的账号间隔，按单账号逐步验收，不因后台保存成功就视为出口已生效。

按项目既有开发和生产发布流程提交、验证与部署。发布前核对当前代码基线，等待在途操作达到可核对状态，保存原暂停开关和发送账本；该优化本身不要求重启微信或重新取钥。回退恢复代码与配置时保留发送事实、未决请求和已承诺保护时间，不通过回滚旧数据库使已经发送的消息再次入队。
