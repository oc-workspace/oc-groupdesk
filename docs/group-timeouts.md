# 按群配置等待时间

在「群管理」选中群，找到「模型等待与请求时效」。前四项以整数秒填写，等待致歉阈值以整数分钟填写，修改后点击「保存配置」，再手动刷新确认状态。每个群独立保存；未设置的旧群和新群默认使用 Planner 300 / Replyer 300 / 接口 310 / 总任务 420 秒，致歉阈值沿用当前的 5 分钟。

| 配置 | 默认 | 允许范围 |
| --- | --- | --- |
| Planner 超时 | 300 秒（5 分钟） | 30—600 秒 |
| Replyer 超时 | 300 秒（5 分钟） | 30—600 秒 |
| 接口请求超时 | 310 秒 | 40—660 秒 |
| 点名请求总有效期 | 420 秒（7 分钟） | 105—1800 秒 |
| 等待致歉阈值 | 5 分钟 | 1—30 分钟（整数） |

接口至少比 Planner、Replyer 中较大的值多 10 秒，总有效期至少比接口多 65 秒，为 Replyer 和发送留时间；前后端均校验，非法设置不会入库。「恢复等待时间默认值」只修改当前表单，仍需保存。

总有效期从首次采集开始，排队、合并和处理共同消耗。同一人的补充、催促或模型重试不会获得新的完整时长。已入队的请求遇到配置版本变化会按原版本门控取消；已活动任务的截止时间不会因为随后延长配置而续期。Planner 与 Replyer 均受本次任务剩余时间限制，排队之后不保证还能获得完整配置时长。

等待致歉也从首次采集开始，包含排队；恰好达到阈值不添加，只有严格超过才在同一条正文前添加当前 Persona、同语言的致歉。阈值高于或等于总有效期时，正常超时前不会触发致歉；不会为了等待致歉延长任务，也不单独发送致歉。普通主动插话 90 秒时效、来源新鲜度、共享模型并发和每日预算继续生效。

## 运行时契约

群 policy JSON 的 `timeouts` 新增 `replyer_seconds`，致歉阈值仍用 `wait_apology_seconds`（整分钟换算的秒数）。迁移 015 为现有群补充 Replyer 默认 300 秒；若某群接口超时低于 310 秒，则取接口超时减 10 秒，保留其原有短等待方案。迁移增加受影响群版本并清除旧确认。运行时配置下发 `timeout_policy_contract_version: 3`；适配器校验并实际应用后，ACK 必须带 `timeout_policy_version: 3`。v1/v2 机器人不能误确认 Replyer 新设置。模型路由和 Persona 的既有能力确认仍需一起提交。

通用 `GroupDeskClient.applyConfig` 的 apply 回调须在真正应用后返回 `{timeout_policy_version: 3, ...}`，可带已有模型/Persona能力字段。未返回匹配能力或应用抛错时不发送 ACK。更新后的机器人和客户端兼容 v1/v2 后台，只有读取到 v3 策略才声明 v3，方便先更新机器人再发布后台。

MaiBot 接入以来源群为准读取参数；Planner 与 Replyer 在原生任务超时包装处使用请求内数值，不修改共享任务配置。私有模型路由生成带接口超时标识的提供商名，以隔离原生按名称缓存的 SDK 客户端；同一 Key 的两个群也不会串用超时。明确使用旧路由的群同样通过请求内复制设置超时，原提供商不变。

## 安装与回退

先部署兼容旧后台的机器人运行代码，再发布后台。`timeout_policy.py`、`groupdesk_runtime.py`、`model_routing.py` 和长等待 `latency.py` 放入已有 limits 目录；`long-wait/install-group-timeouts.py` 只对校验过的原生 `utils_model.py` 副本安装任务超时钩子，重复执行保持字节一致。全局私有 TOML 保留为兼容缺省，无需改写凭据或其他参数。

部署须等待无活动模型任务，保留原收发开关，备份源码及 SQLite，只重建 MaiBot 与桥接。微信容器与登录不重启，数据和预算账本不重置。回退时先回退 GroupDesk 发布，再恢复机器人源码及原开关；保留 SQLite 和新增审计字段。旧机器人不能绕过新版能力门控进行确认。

## 生成重试与共享限额

当前 root2 私有运行参数为每任务最多 5 次模型调用、Replyer 最多 2 次，即允许一次生成重试。Planner 仍最多 2 次，Utils 与 Fast Model 各最多 1 次；所有阶段同时受 5 次总上限约束，每分钟最多 8 次、每日 10M token 不变。失败、超时和重试均占调用数；无法取得用量时保守计入预留预算。

Replyer 的 300 秒是单次上限，不保证有足够时间完整执行两次。每次开始取配置时长与原任务剩余时长减 5 秒中的较小值。例如已等待 320 秒、总有效期 420 秒，下一次最多约 95 秒。重试不重置排队时间或截止时间，发送去重和权限检查保持有效。
