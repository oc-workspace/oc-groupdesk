# 按群配置等待时间

在「群管理」选中群，找到「模型等待与请求时效」。三项都以整数秒填写，修改后点击「保存配置」，再手动刷新确认状态。每个群独立保存；未设置的旧群和新群默认使用 300 / 310 / 420 秒。

| 配置 | 默认 | 允许范围 |
| --- | --- | --- |
| Planner 超时 | 300 秒（5 分钟） | 30—600 秒 |
| 接口请求超时 | 310 秒 | 40—660 秒 |
| 点名请求总有效期 | 420 秒（7 分钟） | 105—1800 秒 |

接口至少比 Planner 多 10 秒，总有效期至少比接口多 65 秒，为 Replyer 和发送留时间；前后端均校验，非法设置不会入库。「恢复等待时间默认值」只修改当前表单，仍需保存。

总有效期从首次采集开始，排队、合并和处理共同消耗。同一人的补充、催促或模型重试不会获得新的完整时长。已入队的请求遇到配置版本变化会按原版本门控取消；已活动任务的截止时间不会因为随后延长配置而续期。Planner 也受本次任务剩余时间限制，排队之后不保证还能获得完整配置时长。

仅这三项按群配置。Replyer 原有 60 秒上限、超过 120 秒的同语言 Persona 致歉、普通主动插话 90 秒时效、来源新鲜度、共享模型并发和每日预算继续生效。此功能不增加重试或备用模型。

## 运行时契约

群 policy JSON 增加 `timeouts`，字段为 `planner_seconds`、`request_seconds`、`direct_ttl_seconds`。利用已有 JSON 列，无需数据库迁移。运行时配置下发 `timeout_policy_contract_version: 1`；适配器校验完整策略并实际应用后，ACK 必须带 `timeout_policy_version: 1`。缺少能力确认返回 409，不能显示误报的“机器人已确认”。模型路由和 Persona 的既有能力确认仍需一起提交。

通用 `GroupDeskClient.applyConfig` 的 apply 回调，须在真正应用后返回 `{timeout_policy_version: 1, ...}`，可带已有模型/Persona能力字段。未返回等待策略能力或应用抛错时，不发送 ACK。

MaiBot 接入以来源群为准读取参数；Planner 在原生任务超时包装处使用请求内数值，不修改共享任务配置。私有模型路由生成带接口超时标识的提供商名，以隔离原生按名称缓存的 SDK 客户端；同一 Key 的两个群也不会串用超时。明确使用旧路由的群同样通过请求内复制设置超时，原提供商不变。

## 安装与回退

先部署兼容旧后台的机器人运行代码，再发布后台。`timeout_policy.py`、`groupdesk_runtime.py`、`model_routing.py` 和长等待 `latency.py` 放入已有 limits 目录；`long-wait/install-group-timeouts.py` 只对校验过的原生 `utils_model.py` 副本安装 Planner 钩子，重复执行保持字节一致。全局私有 TOML 保留为兼容缺省，无需改写凭据或其他参数。

部署须等待无活动模型任务，保留原收发开关，备份源码及 SQLite，只重建 MaiBot 与桥接。微信容器与登录不重启，数据和预算账本不重置。回退时先回退 GroupDesk 发布，再恢复机器人源码及原开关；保留 SQLite 和新增审计字段。旧机器人不能绕过新版能力门控进行确认。
