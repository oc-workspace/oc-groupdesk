# 群聊回复可靠性

当模型网关拒绝结构化历史时，GroupDesk 在明确收到 HTTP 400 或 422 后，将可移植文本历史转换为单条用户输入并保留独立系统指令，只重试一次。历史角色、工具调用 ID 和结果作为引用记录保留，当前工具定义与输出上限沿用原请求。图片、文件和不透明原生推理记录无法安全转换时停止降级。

每个上游请求独立预约并结算用量，兼容重试共用原超时时间和取消信号。上游 4xx 保留状态码与固定错误代码，上游原始错误正文不写日志、不返回浏览器。5xx 继续按临时网关故障处理。

## 运行端

install.py 对既有 limits/policy.py、limits/group_guard.py、bridge/app.py 和 patched/reasoning_engine.py 做精确、可重复应用的补丁，并安装 chat_reliability.py。所有文件语法检查通过后才写入。部署时先复制候选目录预检和测试，再备份并更新对应程序文件。

- 最终 Planner 失败及时释放活动任务。Replyer 可使用已配置的一次生成重试，重试额度耗尽后释放。已在途模型请求、发送预约和待核实发送均保留保护。
- 正常回答在跨进程发送前标记“微信发送中”。循环结束不会把它当作无回复。记录、监控与提示词渲染的终结步骤最多等待 5 秒；失败后的新任务等待这段清理完成，使用 7 秒保护间隔，成功任务沿用配置间隔。
- 30 秒合并窗口内沿用原逻辑。超过窗口的新直接请求复用持久化延后队列，依照后台现有“允许补答”和有效分钟数配置，默认 10 分钟，最多 100 个待补记录。关闭补答时沿用不延后行为。原消息时间和微信成员目标保留，重启不重置有效期。
- 只有明确失败、未进入发送、仍在 10 分钟内的点名请求才可发送一次失败说明。说明走原有语言、群版本、配额、原生 @ 与发送去重守卫。发送前持久预约，结果不明时留待核实。
- 请求阶段从现有约 30 秒配置同步循环上报。后台每群显示最近十条记录，点击“刷新确认状态”更新。上报字段只含不透明请求 ID、阶段、时间和固定原因，不上传聊天正文或凭据。微信可用性仍每小时巡检。

## 验证

test_reliability.py 使用临时 SQLite 与合成任务验证失败释放、模型预约保护、发送在途保护、Replyer 重试、重启去重和终结超时。test_native_queue.py 在已打补丁的真实 Policy 上验证超合并窗口排队、原成员目标、去重、过期和关闭行为。测试需提供原生 Policy 依赖和静态限额配置，连接与快照路径应指向不存在的合成路径。

服务端回归覆盖请求转换、指令边界、多媒体拒绝、独立计量、第二次失败停止、取消、暂态错误和按群授权。实群不发送测试消息。发布后通过合成模型请求、后台记录和运行端只读状态验收。
