# 每小时可用性巡检

主程序、微信和桥接继续运行在原Docker容器内。宿主机已有Python/systemd执行轻量运维调度，不依赖Mac、Codex会话或大模型。timer每整点运行一次；发现故障后，仅在当轮进行有限恢复和短暂复查，不新增30秒周期巡检。消息采集和配置同步保持原频率。

## 状态与动作

- 健康但群内安静：保持安静，不发送测试消息、不调用模型。
- 管理员通过ops.py暂停：报告维护状态，不自动恢复收发。
- 明确的登录按钮：只在没有聊天编辑器、没有会话列表且登录窗口无歧义时点击一次。
- 手机确认、二维码或电脑锁定：停止自动尝试，通知管理员绑定的独立微信通道。
- 微信进程消失：保留/config，从已有桌面会话启动微信。
- 界面读取异常：先重启bowxt读取服务，不重启微信。
- MaiBot或桥接异常：仅重启对应容器，有有效活动任务时暂缓。容器已停止则通知，尊重Docker手动停止状态。
- 每小时最多两次恢复动作，单轮不会反复执行同一动作。

`desktop_control.py`部署至持久化的/config/bowxt/availability_desktop.py，以abc用户执行。只返回状态，不返回聊天正文或界面截图。不能代替手机验证，也不能保证微信会提供免确认登录能力。

## 通知与恢复后行为

告警通过指定接收方扫码绑定的Server酱Turbo微信通道发送，独立于小T的微信登录。管理员在GroupDesk系统设置保存SendKey并确认接收方已绑定；凭据加密保存，只向对应适配器下发。这里的微信号是接收方说明，不能代替接收方扫码绑定。未绑定时后台明确显示待配置，通知保留待重试，不改发Telegram。

首次健康检查不发通知；故障状态变化与恢复才通知，同一故障不每小时提醒。每天最多尝试成功提交5条，失败保留待重试状态。请求受理不等于接收方实际收到，可在后台发送验证通知核对。只发送技术状态，不发送群聊天正文。

恢复后固定核对**恢复上线前12小时**内的点名（原名与别名、可靠的@标记），分别处理每个已授权群。取消无条件的英文上线公告：只有发现可验证的未回复点名，才把简短道歉与第一条补答合在一起；没有遗漏则保持安静。道歉优先英文，若群语言策略不允许英文则遵守本群语言范围；补答跟随原成员语言，继续绑定当前已发布Persona或原GT Skill。不让群友重发。

`recovery.py`在原正常入站中保存来源序号、首次采集时间、原文及对应任务ID，保留48小时用于12小时窗口核对；不是全群无限期历史归档。只有已确认incoming、text且发送者已识别的授权群消息可进入正常链路。已成功发送的任务排除；reserved/uncertain等不确定发送进入人工核查，避免重复。合并同一群同一发送者的遗漏，任务ID、来源批次和事故ID持久化，重复巡检不重复排队。

补答先等现有任务结束，再按普通点名门控进入：仍共享每日Token、调用次数、群回复总量、成员间隔、模型并发、语言和配置版本。历史原时间不改写；补答作为明确标注的新运维任务，普通消息90秒过期规则不变。模型看到可信补答说明和原始采集时间，不能声称已获得完整群史。原任务还在处理时等待其结果，若原任务随后成功则取消补答。单个补答仍只发一条；超过输入上限的合并、模型失败、不确定发送、排队一小时仍无法获准的任务保留核查状态，不循环重试或突发补发。

**覆盖限制：**Linux微信不保证恢复离线期间所有消息，UI也可能只提供共享时间分隔标签。这里的时间使用首次采集时间，不冒充逐条原始发送时间。未同步记录不能核对；上线前没有来源—任务关联的旧记录也不能自动判定“没回复”。扫描结果使用recorded_only/partial_untracked标记，不把空结果宣称为“期间无人点名”。这些情况不在群里发通用解释，留管理员核查。

已有消息接收请求发生持续30秒以上错误时，仅记录该请求的失败/成功时间，不增加额外巡检请求。即使在两次整点之间恢复，下一次每小时巡检也会根据持久记录核对；自动补答可能等到下一整点，不承诺即时上线公告。

GroupDesk使用专用适配器token接收/api/runtime/health，每群独立授权。健康报告不递增配置revision，不充当配置ACK。后台超过75分钟未收到报告则显示待确认；管理员点击现有刷新按钮更新页面。平台本身断网、整机关闭时，服务器内的检查器不能向外发送通知。

## Swap配置

当前实施目标为宿主机2GiB持久化swap；微信物理内存保持1664MiB，memory+swap总上限3712MiB。使用docker update在线应用，再同步Compose的memswap_limit，不重建当前微信容器。swap由宿主机内核提供，不是新安装的应用服务。

swap只是峰值缓冲，不能修复持续增长。保留每小时内存/swap采样；不关闭OOM保护，不把内存设为无限。恢复前备份fstab、Compose和原容器限制。回退时先停timer，保留正在使用的swap；只有确认宿主机有足够余量容纳换回内存后再swapoff，不能直接删除正在使用的文件。

## 安装与验收

把monitor.py放在服务器项目availability/，把recovery.py放入limits/，使用install-recovery.py对既有policy.py、group_guard.py与bridge/app.py安装幂等钩子，复制desktop_control.py到持久化目录。修改核心/桥接代码时只重建相应两个容器，不重启微信。安装.service/.timer到/etc/systemd/system，daemon-reload后先手动执行一次service，确认状态上报，再enable --now timer。

monitor状态保存在/opt/persist/maibot-wechat/availability/state.json，权限0600。查看：systemctl status maibot-availability.timer、journalctl -u maibot-availability.service。停止巡检：systemctl disable --now maibot-availability.timer。日常维护仍使用原ops.py pause/resume。

测试：安装钩子后的既有limits代码加入PYTHONPATH，再运行python3 -m unittest discover -s integration/maibot/availability -q；单独monitor测试不依赖MaiBot。故障测试使用Fake驱动，不断开真实微信、不发送测试消息、不调用模型。实际登录点击只在真实故障出现时触发。
