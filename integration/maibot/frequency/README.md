# 全局回复频率与限流补答

后台入口：系统设置 → 全局回复频率与限流补答。

- 时间窗口、次数都可以修改，最多四个不同的滚动窗口，分别为1–1440分钟、1–1000次；所有窗口同时约束。默认仍为5分钟6次、60分钟36次。
- 当前root2三个群使用同一执行端和SQLite额度台账，因此共享额度。多个独立执行端不构成分布式共享计数。
- 每日240次、每日token预算、模型并发、成员30秒间隔等保持原配置。入场按任务计数，最终沉默也占一次；发送端独立计数，reserved/不确定状态同样计入，避免重复发送。
- 补答开关默认开启、有效期默认10分钟，可设1–60分钟。只处理因滚动频率受限的真实点名和已确认的同人跟进；普通主动插话不补。因每日上限、预算、权限、话题或连续轮数受限不因此绕过。
- 有效期从原消息时间起算，与等待、模型生成、提交发送共用。它替代这条受限请求原有的7分钟截止时间，正常未限流请求仍保持原有时效。额度不足直到过期就取消，不保证在时限内完成。缩短时效立即约束已有等待；增加时效不延长已有等待记录。关闭开关取消待补消息，不因重新勾选而复活。

## 数据与确认

`014_reply_frequency.sql`增加全局单行策略和群级`reply_frequency_applied_revision`。保存采用乐观版本检查，内容相同不递增；改变策略只清除频率确认，不改变各群的Persona、话题、模型或群配置revision，也不撤销普通群配置。runtime配置包含独立版本1契约和当前全局revision；ACK必须同时携带已应用的能力与revision。系统设置里的“刷新频率确认状态”单独检查启用群全部确认。

原生`reply_frequency.for_config`只接受所有群一致的全局频率版本；混合版本拒绝执行，等待下一次同步。旧后台和未托管测试夹具保留原生行为，避免提前打开补答。

## 执行与防重

`frequency_waiting`在本地SQLite按原消息seq持久排队。最多100个待处理/催促记录，队列满有明确结果和指标；不会无限堆积。相同原消息不会重复入场；纯催促指向原等待记录，共用原时效，不另开任务。真正的新问题保留自己的时间和记录。到期、关闭、权限变化不会把历史消息伪装成刚收到。

额度释放且普通排队/活动任务为空时，最多提升一条到既有pending队列，保留群、发送者、原始问题及当前策略版本。群配置revision变化会取消旧等待，临时连接/权限不可用则等待但不执行。断线恢复任务让当前实时等待优先；离线恢复核对跳过已在此队列的来源，避免同一条同时补两次。

已排队后才撞到频率也可获得固定的补答截止时间。生成后发送端若恰好受限，在尚未提交微信之前等待额度，复用同一结果和发送ID，不重新调用模型。发送前重查权限/版本、语言、截止时间和发送开关。完成或状态不确定的发送保留既有去重和人工核对规则，不自动重发。排队源记录可跨重启保留；进程若在生成后的内存等待阶段退出，不自动重放不确定发送。

`install-native.py`针对已核对的生产源码做全文件摘要与逐hunk校验，全部通过后才写入；未知基线拒绝，重复安装幂等。部署保留当前chatlog Compose叠加文件，只重建MaiBot和bridge，保留私有模型配置、额度台账、数据库读取器与微信客户端。

验证使用合成数据、断网原生Docker与独立PostgreSQL，不向真实群发送测试。适用限流补答从上线后新收到的消息开始，不批量重放旧的被丢弃消息。
